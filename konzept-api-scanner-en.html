Integration: Thomas’ Android App, Web Scanner & lwhub.de

Automated data reconciliation of member lists, power, donations, VS points & events – including archive restoration and cross-alliance transfer via API.

🎯 1. Goals & Core Requirements

Thomas is developing an Android app (Last-War-Tracker with MediaProjection & ML Kit OCR), while our Web Scanner (RapidOCR) runs on the desktop. Both tools should connect seamlessly with lwhub.de.

📋 Fetch the member list

Scanner and app load the current name list including known aliases/spellings, so OCR errors can be corrected immediately.

🔄 Intelligent data reconciliation

When a member is detected, the backend automatically checks: Is it active? Is it in the archive? Is it in a partner alliance?

🚀 Transfer & restore via API

No duplicate records: archived players are reactivated; players who switched from other alliances are transferred automatically.

⚔️ Power, donations, events

Extending the data model for historical time series (power, daily/weekly donations, VS points, kills, Desert Storm, Zombie Siege).

🛡️ Rank matching & rank detection

The rank is read exclusively from the number on the golden shield icon (R1–R5) – the rank name is ignored because every alliance defines its own labels. The scanner rank is reconciled with the stored rank during sync.

🧠 2. The “Smart-Insert” Decision Tree

Players often switch between main and alternate alliances or pause in the archive. When a name is captured, the API runs the following workflow:

1. Name detected by the scanner (e.g. “Lion Tooth”) Scan Input
Whether via Thomas’ phone or the Web Scanner – the name arrives via batch sync.
↓
Detect the rank from the shield (number R1–R5) Shield Number = Rank
Per entry the client sends the rank only based on the number on the golden shield icon. The rank name next to it is ignored because every alliance defines its own labels. R1–R4 are detected on the rank bar between the member cards (shield on the left, member count on the right), R5 on the shield next to the alliance leader’s name.
↓
Case A: Already active in the target alliance? Standard Update
Action: Update current values (power, HQ level, status) + write a new data point into player_metrics. Rank check: the scanner rank (shield number) is compared with the stored rank; deviations go through applyProtectedRankRule + logRankChange (protected R4 always stays R4).
↓ No
Case B: Is the player in the archive (archived_players)? Automatic Restore
Action: The player is fully restored from the archive. Their previous player_id, Discord ID and past weekly entries are preserved. The alliance is set to the target alliance.
↓ No
Case C: Is the player active in ANOTHER alliance? Alliance Transfer
Action: API transfer analogous to the internal R5 transfer function. Player, identity, name history and entries are rewritten to the new alliance (without data loss).
↓ No
Case D: Completely new player New Record
Action: Regular INSERT INTO players with a new UUID and the first entry in the name history.
–
Rank rules (apply in all cases) Protected & Honor Roles
Protected R4 names (config INY_PROTECTED_R4_NAMES, e.g. “Lion Tooth”) always stay at rank 4 in all cases A–D – even on restore and transfer. If the scanner reports a different shield number (e.g. R3 or R5), it is blocked and documented in the rank_change_log; enforceProtectedRanks additionally guarantees rank 4. Honor members (honor_member) are read-only (can_write = false): the scanner may not overwrite their rank. Rank codes are limited to 1–5 (safeRank, otherwise default 3).

Rank detection: shield icon instead of rank name

The scanner detects the rank only from the golden shield icon (R1–R5) in the member list – the number on the shield is the rank code. The rank name next to it must not be used, because every alliance defines its own labels.

  • R1–R4: rank bar between the member cards (shield on the left, member count + arrow on the right). A bar only exists as long as members are assigned to that rank; its position can change when scrolling/expanding.
  • R5: no bar of its own – the R5 shield is at the top next to the alliance leader’s name.
  • Current state: group_ranking_rows captures the shield as rank_badge (RANK_BADGE_RE = ^R[1-5]$), R5 via the leader banner (find_leader_card). Matching uses default_rank || current_rank_code || 3 from the API list; the shield is currently only displayed.
  • Target state (Phase 4): the sync payload in matching.js should write the shield number as a numeric rank code (1–5) into the rank/default_rank field of each entry – so far the rank field is missing in the syncToLwHub payload.
  • Always R4 (protected): “Lion Tooth” stays at rank 4 via INY_PROTECTED_R4_NAMES regardless of the OCR result – a misread shield number is blocked by applyProtectedRankRule.

🗄️ 3. Data Model Extension (100% compatible)

The existing page (lwhub.de) and the table system for ranks and flags must never be disturbed. Therefore we extend the schema purely additively:

A. Current snapshot values directly in players

For lightning-fast access in the member list and the web admin:

ALTER TABLE players 
    ADD COLUMN current_power BIGINT NULL DEFAULT NULL,
    ADD COLUMN hq_level TINYINT NULL DEFAULT NULL,
    ADD COLUMN last_scanned_at DATETIME NULL DEFAULT NULL,
    ADD COLUMN last_seen_status VARCHAR(100) NULL DEFAULT NULL;

B. Universal time-series table player_metrics

Records every single scan. Works for power, donations, kills and any future events:

CREATE TABLE IF NOT EXISTS player_metrics (
    metric_id CHAR(36) NOT NULL,
    alliance VARCHAR(50) NOT NULL,
    player_id CHAR(36) NOT NULL,
    metric_type VARCHAR(40) NOT NULL, -- 'POWER', 'DONATION_WEEK', 'DONATION_DAY', 'VS_WEEK', 'VS_DAY', 'KILLS', 'DESERT_STORM', etc.
    value_numeric BIGINT NULL,
    value_text VARCHAR(255) NULL,
    extra_json JSON NULL,             -- e.g. Task Force A/B, completed waves in Zombie Siege
    source VARCHAR(50) NOT NULL,      -- 'android_app', 'web_scanner', 'manual'
    recorded_at DATETIME NOT NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (alliance, metric_id),
    KEY ix_metrics_player (alliance, player_id, metric_type, recorded_at),
    KEY ix_metrics_type_time (alliance, metric_type, recorded_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

C. API tokens for app and scanner api_tokens

CREATE TABLE IF NOT EXISTS api_tokens (
    token_id CHAR(36) NOT NULL,
    alliance VARCHAR(50) NOT NULL,
    token_hash VARCHAR(128) NOT NULL,
    client_name VARCHAR(100) NOT NULL, -- e.g. 'Thomas Android App', 'Desktop Scanner'
    role VARCHAR(20) NOT NULL DEFAULT 'scanner', -- 'scanner', 'normal', 'r4', 'r5' (analogous to roleFromRank)
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    last_used_at DATETIME NULL,
    is_active TINYINT(1) NOT NULL DEFAULT 1,
    PRIMARY KEY (token_id),
    KEY ix_token_hash (token_hash)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

🔌 4. New & Extended API Interfaces

Authentication

All requests from Thomas’ app or the scanner send a Bearer token in the HTTP header:

Authorization: Bearer lwhub_sec_xxxxxxxxxxxxxxxxxxxxxxxx

1. Fetch the member list: GET /api/members

Returns the active member list including aliases for OCR name matching. Field names exactly as in handleGetMembers:

// Response (200 OK)
[
  {
    "id": "e3a89012-...",
    "alliance": "NxU1",
    "name": "Lion Tooth",
    "default_rank": 4,          // rank code 1–5 (safeRank), default 3
    "role": "r4",               // 'normal' | 'r4' | 'r5' (roleFromRank)
    "honor_role": null,         // 'honor_r4' | 'honor_member' | null
    "can_manage": true,         // effectiveRank >= 4
    "can_write": true,          // false for honor members (read-only)
    "current_power": 164200000,
    "hq_level": 31,
    "last_seen_status": "Online",
    "last_scanned_at": "2026-10-12 18:30:00",
    "aliases": ["LionTooth", "Lion Tooth", "L1on Tooth"]
  },
  ...
]

2. Batch sync of scan sessions: POST /api/scans/sync

Allows uploading a complete capture session (e.g. 100 members) in a single atomic transaction:

// Request Body
{
  "alliance": "INY",
  "scan_type": "POWER", // or 'DONATION_WEEK', 'VS_DAY', 'MEMBERS_LIST'
  "recorded_at": "2026-10-12T19:00:00Z",
  "source": "android_app",
  "options": {
    "auto_restore": true,    // automatically restore players in the archive
    "auto_transfer": true   // transfer players from partner alliances
  },
  "entries": [
    {
      "name": "Lion Tooth",
      "value_numeric": 164200000,
      "hq_level": 31,
      "rank": 4,          // shield number R1–R5, not the rank name
      "status": "Online"
    },
    {
      "name": "Returnee77",
      "value_numeric": 120500000,
      "hq_level": 30
    }
  ]
}

Note on ranks: per entry rank (or default_rank) is accepted – analogous to handleAddMember/handleUpdateMember ($body['default_rank'] ?? $body['rank'] ?? 3). The transmitted value is always the shield number R1–R5 (not the rank name), limited to 1–5 (safeRank, otherwise default 3). Protected R4 names (e.g. “Lion Tooth”) always stay at rank 4; honor members are read-only and are not overwritten. Blocked deviations end up in the rank_change_log and are reported back as conflicts.

// Response (200 OK)
{
  "ok": true,
  "summary": {
    "total": 2,
    "updated": 1,
    "restored_from_archive": 1,
    "transferred": 0,
    "created_new": 0
  },
  "details": [
    { "name": "Lion Tooth", "action": "updated", "player_id": "e3a89012-...", "rank": 4 },
    { "name": "Returnee77", "action": "restored_from_archive", "player_id": "7b0198aa-...", "rank": 3 }
  ],
  "conflicts": [
    {
      "name": "ExamplePlayer",
      "scanned_rank": 2,
      "kept_rank": 4,
      "blocked": true,
      "reason": "protected-r4-member"
    }
  ]
}

3. Targeted transfer via API: POST /api/members/{name_or_id}/transfer

Performs the same safe transfer as the internal R5 tool – now fully script- and app-capable:

// Request Body
{
  "to_alliance": "INY"
}

// Response (200 OK)
{
  "ok": true,
  "player_id": "e3a89012-...",
  "player_name": "Lion Tooth",
  "from_alliance": "NxU1",
  "to_alliance": "INY"
}
